# 주석 작성 방법

## 목적

이 문서는 현재 `apps/user`, `apps/admin`의 몇 개 모듈을 기준으로 주석을 어떤 단위와 형식으로 달면 좋은지 정리한 가이드입니다.

주석은 코드가 이미 말해 주는 내용을 반복하기보다, 다음 정보를 남기는 데 사용합니다.

- 외부에서 사용하는 계약: props, request/response, 반환값
- 코드만 보고는 바로 알기 어려운 의도: UX 정책, API 호출 시점, 상태 복구 조건
- 유지보수자가 실수하기 쉬운 경계: 기본값, optional 값, 0-based/1-based 인덱스, 캐시 key 구조

## 기본 원칙

1. 공개 export를 우선 설명합니다.
   - 컴포넌트, 훅, API 함수, 타입, 상수 객체처럼 다른 파일에서 가져다 쓰는 대상이 우선입니다.
2. 구현 내부 주석은 복잡한 의도에만 답니다.
   - 예: 포커스 순환, 페이지 번호 보정, sessionStorage 복구, API 응답 DTO를 화면 모델로 변환하는 부분
3. 값의 단위와 기준을 명확히 씁니다.
   - 예: `1-based`, `0-based`, `deg/frame`, `밀리초`, `기본값 5`
4. 오래될 가능성이 큰 주석은 피합니다.
   - 파일 목록, CSS 클래스 의미, 단순 JSX 구조처럼 자주 바뀌는 내용은 코드 자체를 믿습니다.
5. 한국어로 작성합니다.
   - 이 저장소의 JSDoc과 문서는 한국어 설명을 기본으로 합니다.

## 모듈별 작성 방식

### 1. React 컴포넌트

컴포넌트 JSDoc은 `@param` 대신 `@prop`를 사용합니다.

작성 순서는 아래를 따릅니다.

1. 한 줄 요약
2. `@prop` 설명
3. 필요한 보충 설명
4. `@example` 하나

예시:

````tsx
type PaginationProps = {
  page: number;
  totalPages: number;
  onPageChange: (page: number) => void;
};

/**
 * 페이지 이동 버튼을 렌더링하는 공통 페이지네이션 컴포넌트
 *
 * @prop page 필수, 현재 활성 페이지 번호입니다. 1부터 시작합니다.
 * @prop totalPages 필수, 전체 페이지 수입니다.
 * @prop onPageChange 필수, 페이지 클릭 시 선택된 페이지 번호를 전달합니다.
 *
 * 5페이지 단위로 페이지 번호를 끊어 노출합니다.
 *
 * @example
 * ```jsx
 * <Pagination page={page} totalPages={5} onPageChange={setPage} />
 * ```
 */
export const Pagination = ({
  page,
  totalPages,
  onPageChange
}: PaginationProps) => {
  // ...
};
````

체크 포인트:

- `@prop` 이름은 실제 props 이름과 반드시 맞춥니다.
- optional 여부와 기본값이 있으면 설명에 씁니다.
- 예시는 실제 props shape와 맞는 `jsx` fenced code block 하나만 둡니다.
- 컴포넌트 내부 JSX에는 단순 마크업 설명 주석을 달지 않습니다.

### 2. 훅

훅은 호출자가 알아야 하는 동작, 입력값, 반환값을 설명합니다.

- 입력 파라미터가 있으면 `@param`
- 반환 객체가 있으면 `@returns` 또는 `@returns.xxx`
- UI 정책이나 side effect가 있으면 본문 설명에 작성

예시:

```ts
/**
 * 모달 내부에서만 Tab 포커스가 순환하도록 가두는 훅
 *
 * 모달이 열릴 때 첫 번째 포커스 가능 요소로 포커스를 이동하고,
 * Tab/Shift+Tab 이동이 컨테이너 밖으로 나가지 않도록 막습니다.
 *
 * @param ref 포커스를 가둘 컨테이너 요소의 ref입니다.
 *
 */
export function useFocusTrap(ref: RefObject<HTMLElement | null>) {
  // ...
}
```

반환 객체가 화면에서 바로 쓰이는 훅은 아래처럼 key 단위로 설명합니다.

```ts
/**
 * 히스토리 목록 응답에서 연도/행사명 필터 옵션을 누적 생성하는 훅입니다.
 *
 * 검색 조건으로 목록이 일시적으로 좁아져도 이전에 확인한 옵션을 유지합니다.
 *
 * @param list 필터 옵션을 추출할 히스토리 목록입니다.
 * @param options 옵션 value 생성 전략입니다.
 * @returns 필터 카드에 전달할 옵션 집합입니다.
 * @returns.yearOptions 연도 드롭다운용 문자열 배열입니다.
 * @returns.eventNameOptions 행사명 드롭다운용 `{ label, value }` 배열입니다.
 */
export const useHistoryFilterOptions = (list, options) => {
  // ...
};
```

### 3. API 함수

API 함수 주석은 "언제/무엇을 요청하는지"를 짧게 설명합니다.

예시:

```ts
/**
 * 페이지 진입 시 출석체크 정보 조회
 */
export const getAttendanceInfo = async (
  params: AttendanceInfoRequest = getCurrentAttendancePeriod()
): Promise<AttendanceInfoResponse> => {
  // ...
};

/**
 * 룰렛 회전 결과 요청 (Stop 버튼 클릭 시)
 */
export const spinRoulette = async (): Promise<RouletteSpinResponse> => {
  // ...
};
```

체크 포인트:

- URL 문자열은 `constants`에 있으므로 API 함수 주석에서 반복하지 않습니다.
- `GET`, `POST` 같은 method는 함수명만으로 부족하거나 상수/타입 문맥에서 도움이 될 때만 씁니다.
- 서버 DTO를 화면 모델로 바꾸는 함수가 있으면 변환 의도를 설명합니다.
- 임시 하드코딩 값이 있으면 왜 필요한지 또는 언제 제거할지 주석으로 남깁니다.

### 4. 타입과 DTO

API request/response 타입은 필드 의미를 남기는 것이 좋습니다.

현재 타입 파일에서는 `@field` 패턴을 사용하고 있습니다.

```ts
/**
 * FAQ 목록 조회 API 응답 타입
 *
 * @field list FAQ 목록입니다.
 * @field totalCount FAQ 전체 개수입니다.
 * @field totalPage FAQ 전체 페이지 수입니다.
 * @field pageIndex 현재 페이지 번호입니다.
 * @field pageSize 페이지당 조회 개수입니다.
 */
export interface FAQListResponseData {
  list: FAQItem[];
  totalCount: number;
  totalPage: number;
  pageIndex: number;
  pageSize: number;
}
```

체크 포인트:

- DTO는 서버 필드 이름과 화면에서 쓰는 이름이 다르면 그 차이를 설명합니다.
- 상태값 union은 각 literal의 의미를 적습니다.
- 단순히 타입 이름을 풀어 쓰는 주석은 생략합니다.

### 5. 상수

API endpoint, query key, 공통 옵션처럼 여러 모듈에서 공유하는 상수는 한 줄 JSDoc이 효과적입니다.

```ts
export const END_POINTS = {
  /** [GET] 대시보드 종합 데이터 조회 API 경로 */
  DASHBOARD: '/admin/dashboard',

  /** 관리자 행사관리 API 경로 */
  MANAGE_EVENT: {
    /** [GET] 행사 목록 조회 API 경로 */
    LIST: '/admin/events'
  }
} as const;
```

체크 포인트:

- endpoint는 `[GET]`, `[POST]`, `[PUT]`, `[DELETE]`를 앞에 붙이면 검색과 검토가 쉽습니다.
- query key는 도메인 구분 주석과 key별 설명을 간단히 둡니다.
- 숫자 상수는 단위를 inline comment로 붙여도 됩니다.

```ts
export const REFETCH_INTERVAL = 5 * 60 * 1000; // 5분
```

### 6. store와 상태 복구 로직

Jotai atom이나 sessionStorage 복구처럼 상태 흐름이 중요한 파일은 섹션 주석과 조건 주석을 같이 씁니다.

```ts
// ── 모달 타입 등록부 ───────────────────────────────────────────
// 새 모달을 추가할 때 타입과 props를 여기에 추가합니다.

export type ModalConfig =
  | { type: 'terms'; props: TermsModalProps }
  | { type: 'alert'; props: AlertModalProps };

// ── atom ──────────────────────────────────────────────────────
// stack 구조 → 여러 모달을 순서대로 쌓을 수 있습니다.
export const modalStackAtom = atom<ModalConfig[]>([]);
```

체크 포인트:

- 상태 필드마다 주석이 필요하면 "어느 step에서 생성/사용되는지"를 적습니다.
- storage 복구는 "검증을 통과할 때만 복구", "비어 있으면 key 제거"처럼 조건을 남깁니다.
- setter 내부의 단순 대입은 주석을 달지 않습니다.

### 7. 유틸 함수

유틸 함수는 입력 보정, fallback, 반환 shape를 설명합니다.

```ts
/**
 * 페이지네이션 목록 응답을 화면에서 바로 사용할 수 있는 기본값 형태로 정리합니다.
 *
 * @param data API 응답의 페이지네이션 데이터입니다.
 * @param fallbackPageIndex 응답에 현재 페이지 정보가 없을 때 사용할 기본 페이지 번호입니다.
 * @returns list, totalCount, totalPages, currentPageIndex, pageSize를 안전한 기본값과 함께 반환합니다.
 *
 */
export function getPaginatedListState<T>(
  data: PaginatedListData<T> | undefined,
  fallbackPageIndex: number
) {
  // ...
}
```

체크 포인트:

- 보정 규칙이 있으면 "음수면 1로 처리", "응답 값이 없으면 fallback 사용"처럼 구체적으로 씁니다.
- 제네릭 타입이 핵심이면 `@typeParam`을 사용합니다.
- 내부 계산식의 의도가 어렵다면 해당 줄 위에 짧게 설명합니다.

## 모듈을 돌며 주석을 추가하는 순서

여러 모듈에 주석을 정리할 때는 아래 순서로 진행합니다.

1. 대상 기능의 진입점과 공개 export를 먼저 찾습니다.
   - `components`, `hooks`, `api`, `types`, `constants`, `store`, `utils`를 우선 확인합니다.
2. 타입/상수부터 주석을 맞춥니다.
   - props, request, response, endpoint, query key의 의미가 정리되어야 다른 주석도 짧아집니다.
3. API와 query/hook 계층에는 호출 시점과 반환 계약을 남깁니다.
   - `docs/api-작성순서.md`의 `types -> constants -> api -> queryKeys -> queries -> hooks -> component` 흐름을 따릅니다.
4. 컴포넌트에는 props와 사용 예시를 남깁니다.
   - JSX 내부에는 복잡한 분기나 접근성 의도 외에는 주석을 줄입니다.
5. store/util에는 보정 규칙과 부수효과를 남깁니다.
   - sessionStorage, focus trap, pagination 계산처럼 동작 의도가 중요한 곳만 설명합니다.
6. 마지막으로 오래된 주석을 제거합니다.
   - 코드와 다른 설명, 임시 메모, "이거 쓰면 됨"처럼 맥락이 부족한 주석은 정리 대상입니다.

## 피해야 할 주석

```ts
// page에 1을 더한다
const nextPage = page + 1;
```

위처럼 코드 그대로 읽히는 설명은 피합니다.

```ts
// TODO 나중에 수정
```

담당자, 조건, 제거 기준이 없는 TODO도 피합니다. 필요하면 아래처럼 씁니다.

```ts
// TODO: 실제 관리자 ID가 인증 응답에 포함되면 하드코딩 값을 제거합니다.
```

## 한 줄 정리

이 프로젝트의 주석은 "무엇을 하는 코드인지"보다 "다른 모듈이 어떻게 써야 하고, 왜 그렇게 동작해야 하는지"를 남기는 방식으로 작성합니다.
